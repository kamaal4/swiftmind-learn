UIViewController Lifecycle

Which callback fires when, and what work belongs in each one.

Beginner○Not started8 min
On this page

  • Quick check
  • Interview question

A view controller's lifecycle splits into two groups, and keeping them straight is most of the battle.

Loading happens once. loadView creates the view, viewDidLoad runs immediately after — one time, ever, for that instance.

Appearance happens every time. viewWillAppear, viewDidAppear, viewWillDisappear, viewDidDisappear fire on each transition on and off screen. Push a detail screen and come back, and the appearance callbacks run again while viewDidLoad does not.

Layout sits in between: viewWillLayoutSubviews and viewDidLayoutSubviews can run many times, whenever bounds change — rotation, keyboard, split view.

Analogy

Think of a shop unit.

viewDidLoad is the fit-out: shelves installed, wiring done, signage up. It happens once when you take the lease.

viewWillAppear is unlocking the doors each morning — restock, check today's prices, flip the sign. Every single day, because things changed overnight.

Doing the fit-out every morning is wasteful. Checking today's prices only at fit-out means you're showing last month's.

Under the hood

view is a lazy property. Touching it anywhere — including someVC.view.backgroundColor = .red from outside — forces loadView and then viewDidLoad immediately, whether or not the controller is going on screen. That's the cause of the classic bug where viewDidLoad fires far earlier than expected because something read view while configuring.

Appearance callbacks are driven by the containing controller, so a custom container that forgets addChild/didMove(toParent:) will silently never forward them, and the child's viewWillAppear never runs.

viewDidLayoutSubviews can fire many times per transition. It is not the place for expensive work or for anything that itself triggers layout — that's how you get a loop.

deinit won't run if the controller is in a retain cycle, so cleanup you put there — invalidating a timer, removing an observer — silently never happens. That's why the safer home for teardown is viewDidDisappear.

✕Reading view.frame in viewDidLoad

At viewDidLoad the view exists but hasn't been laid out. Its frame is whatever came from the nib or the initial size, not what the user will see — often wrong on a different device size, in landscape, or in a split view.

Anything depending on final geometry — a gradient layer's frame, a corner radius from height, a scroll view's content inset — belongs in viewDidLayoutSubviews, which runs once bounds are settled.

Quick check

You push a detail screen from a list, then tap back. Which callbacks run on the list controller?

  • viewDidLoad, then viewWillAppear and viewDidAppear
  • viewWillAppear and viewDidAppear only
  • Only viewDidAppear
  • None; it was never removed from the hierarchy
Reveal answer

✓ viewWillAppear and viewDidAppear only

The list controller was never deallocated — the navigation controller kept it in its stack — so it isn't reloaded and viewDidLoad doesn't run again. Only the appearance pair fires. This is exactly why refresh logic belongs in viewWillAppear: put it in viewDidLoad and returning from the detail screen shows stale data.

Interview question

What's the difference between viewDidLoad and viewWillAppear, and how do you decide which to use?

Think first, then reveal

viewDidLoad runs exactly once per instance, right after the view hierarchy is created. viewWillAppear runs every time the view is about to go on screen — including when you come back from a screen you pushed.

So the split is one-time construction versus repeated refresh. Adding subviews, activating constraints, setting fonts and colours, wiring up targets: all viewDidLoad, because doing it again would duplicate work and can duplicate subviews. Anything that could have changed while the screen was away goes in viewWillAppear — re-reading a model, updating a badge, restoring navigation bar state, reflecting a setting the user changed two screens deep.

The bug you get from mixing them up is very recognisable: put a data refresh in viewDidLoad and everything looks right on first launch, then the user edits something on a detail screen, comes back, and the list still shows the old value.

For work that should start only once the transition is actually finished — animations, screen-view analytics, becoming first responder — I'd use viewDidAppear, since the view is genuinely on screen by then.

What an interviewer listens for

  • States once-per-instance versus every-appearance clearly
  • Assigns construction to viewDidLoad and refresh to viewWillAppear
  • Names the stale-data bug that results from confusing them
  • Knows viewDidAppear is for post-transition work

Did you know

loadView is the one method you override to replace the view entirely.

Override it and don't call super if you're building the root view in code — but never call it yourself; touching view does it for you.

Key takeaway

viewDidLoad once, appearance callbacks every time, layout whenever bounds change. Put construction in the first, refresh in the second, and anything geometry-dependent in the third.

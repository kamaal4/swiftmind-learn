Observation

@Observable, and how SwiftUI learns which views depend on which properties.

Advanced○Not started8 min
On this page
  • Analogy
  • Diagram
  • Under the hood
  • Quick check
  • Interview question
  • Key takeaway

@Observable is a macro that makes a reference type's properties trackable. A SwiftUI view that reads one of those properties in body is automatically re-rendered when *that property* changes — and not when others do.

That per-property precision is the whole improvement over ObservableObject. With @Published, any change fired objectWillChange, so every observing view re-rendered regardless of what it actually read. With Observation, a view reading only name doesn't care that progress changed.

It also removes the property-wrapper bookkeeping. No @Published on each property, and in a view you use plain let, or @State when the view owns the model's lifetime.

Analogy

ObservableObject was a building fire alarm. Anything happens anywhere and everybody evacuates, whether or not it concerned them.

@Observable is a per-desk notification. You subscribed to the printer queue, so you hear about the printer — the fact that someone changed the thermostat doesn't reach you at all.

You didn't fill in a subscription form either. The system noticed what you looked at.

Under the hood

The macro rewrites each stored property into a computed one that calls access(keyPath:) on read and withMutation(keyPath:) on write, backed by an ObservationRegistrar.

SwiftUI evaluates body inside withObservationTracking, so every property accessed during that evaluation is recorded as a dependency of that view. When one of those properties is mutated, the registrar notifies exactly the views that read it.

Two consequences worth internalising. First, tracking is per *access during body*, so a property read in a method you call from body is still tracked, while one read in a button's action closure is not — that closure isn't part of body evaluation. Second, reading a whole collection tracks the collection, so appending to an array re-renders everything that read it, no matter how granular the model looks.

It's also not SwiftUI-specific: withObservationTracking is in the Observation module and usable from plain Swift.

✕Storing an @Observable model in @State in the wrong view

@State private var model = Model() creates the model once and ties its lifetime to *that view's identity*. Put it in a view that gets recreated with a new identity and the model is rebuilt, silently losing everything in it.

Own the model at the level whose lifetime should match it, and pass it down as a plain let or through the environment. Passing it down doesn't weaken tracking — that works regardless of how the reference arrived.

Quick check

What's the main advantage of @Observable over ObservableObject with @Published?

  • It works with structs as well as classes
  • Dependencies are tracked per property, so a view only re-renders when a property it actually read changes
  • It removes the need for @State anywhere
  • It makes the model thread-safe
Reveal answer

✓ Dependencies are tracked per property, so a view only re-renders when a property it actually read changes

ObservableObject fires one objectWillChange for any mutation, so every observing view re-renders regardless of what it read. Observation records the specific properties accessed during body evaluation and notifies only those views. It's still classes only, it doesn't touch thread safety, and you still use @State to own a model's lifetime.

Interview question

How does SwiftUI know which views to re-render when an @Observable model changes?

Think first, then reveal

It records dependencies by observing what each view actually reads. SwiftUI evaluates body inside withObservationTracking, and the macro has rewritten every stored property into a computed one that reports reads to an ObservationRegistrar. So by the end of evaluating a body, the framework has an exact set of properties that view depends on. Mutating one goes through withMutation, which notifies precisely the views that read it.

The contrast with ObservableObject is the granularity. There, any @Published write fires a single objectWillChange on the whole object, so every view observing it re-renders whether or not the change was relevant. In a screen with one model and twenty views, that's nineteen wasted body evaluations per keystroke. Observation makes that a non-issue without anyone hand-splitting models to work around it.

Two details I'd flag. Tracking is scoped to body evaluation, so a read in a button's action closure isn't a dependency — which is normally what you want. And granularity is per property, not per element: if a body reads an array, appending to it invalidates that view even if it only rendered one element. Fine-grained models don't help there; you need the view structure to match, typically by putting a ForEach row in its own view that reads only its element.

The practical upshot is that most gratuitous re-render problems go away, and the ones left are about view decomposition rather than about observation.

What an interviewer listens for

  • Explains withObservationTracking and the registrar accurately
  • Quantifies the improvement over objectWillChange
  • Knows tracking is scoped to body evaluation, not closures
  • Raises collection granularity as the remaining sharp edge
  • Connects the fix to view decomposition

Did you know

The Observation framework isn't SwiftUI-only.

withObservationTracking(_:onChange:) lives in the standard Observation module and works in plain Swift, including on the server.

Key takeaway

@Observable tracks reads at property granularity during body evaluation, so only views that actually read a property re-render when it changes. Own the model where its lifetime belongs, and pass it down plainly.

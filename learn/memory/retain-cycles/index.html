Retain Cycles

When two objects keep each other alive and ARC can never free either.

Intermediate○Not started8 min
On this page
  • Analogy
  • Diagram
  • The four shapes
  • Quick check
  • Interview question
  • Key takeaway

A retain cycle is a loop of strong references. A holds B strongly, B holds A strongly, and each keeps the other's count at one. Every outside reference can disappear and both counts still sit above zero, so ARC never frees either. Nothing is reachable and nothing is released.

That's a leak, and on iOS it's usually invisible: no crash, no error, just memory that grows a bit every time the user visits a screen. You find it when the app is killed for memory pressure after twenty minutes of use, or you don't find it at all.

Cycles need at least two participants, but they don't need exactly two. Three-object loops and closure-shaped loops are just as common.

Analogy

Two people are holding a door open for each other.

Neither will go through until the other does, and neither will leave. Everyone else has gone home. From outside the building nothing is happening and nobody can reach them, but the door is still occupied and always will be.

Someone has to be willing to walk away first. That's what making one reference weak does: it says this side isn't going to insist.

The four shapes

Where they actually come from

In practice almost every cycle in an iOS codebase is one of four shapes:

  1. A child holding its parent strongly — the example above. Fix: weak var parent.
  2. A strong delegate — the delegating object holds its delegate, which is usually its owner. Fix: weak var delegate, which is why the convention exists.
  3. A closure stored on self that captures self — the object owns the closure, the closure owns the object. Fix: [weak self] in the capture list.
  4. A long-lived observer or subscription that captures self — a Combine AnyCancellable, a timer target, a notification block. The subscription outlives the screen and drags it along.

Recognising the shape is faster than reasoning from first principles each time.

!Assuming no crash means no leak

A retain cycle produces no error, no warning and no crash at the point it's created. The symptom is a memory graph that grows, and the eventual jetsam kill looks nothing like the code that caused it.

The cheapest defence is a deinit with a log on your screens and view models during development. Push and pop the screen; if the log doesn't fire, you have a cycle, and you know exactly which type to look at.

Quick check

Two objects reference each other strongly and every outside reference is dropped. What does ARC do?

  • Detects the objects are unreachable and frees them
  • Frees them at the next memory warning
  • Nothing — both counts remain above zero, so both leak
  • Raises a runtime warning about the cycle
Reveal answer

✓ Nothing — both counts remain above zero, so both leak

ARC only ever looks at one object's count. It has no notion of reachability, no roots to trace from, and no background pass — those are tracing-GC concepts. Each object here still has one strong reference (from the other), so neither count reaches zero and neither is ever freed. Memory pressure doesn't help; the objects are perfectly valid, just unreachable.

Interview question

Explain a retain cycle, and how you'd detect one in a production application.

Think first, then reveal

A retain cycle is a loop of strong references. Because ARC frees an object only when its own count hits zero, and every object in the loop is being retained by another member of the loop, the whole group stays alive after it becomes unreachable. It's a leak with no crash and no error.

For detection I'd work in three layers.

During development, a deinit log on view controllers and view models. Push a screen, pop it, watch for the line. It costs nothing and catches the majority of cycles the day they're introduced, which is when they're cheapest to fix.

When something's suspected, Xcode's memory graph debugger. It renders the actual object graph and marks cycles directly, so you see which reference to weaken rather than guessing. Instruments' Allocations with a repeated push/pop is the companion — if the persistent-object count for a type climbs by one per visit and never comes down, that's your leak, and the generation summary tells you what's accumulating.

In production, you don't see individual cycles — you see the aggregate. Memory-related terminations in MetricKit, and jetsam events in the organizer, tell you memory is the problem and which build regressed. Then you reproduce with the tools above. It's also worth logging peak footprint per session so a regression shows up as a trend rather than as user complaints.

Prevention beats detection though: ownership pointing one way, weak delegates, [weak self] in stored closures, and reviewing subscriptions for what they capture.

What an interviewer listens for

  • Correctly explains why counting can't detect a cycle
  • Gives a layered answer: dev-time, debugging, production telemetry
  • Names concrete tools — memory graph debugger, Allocations, MetricKit
  • Mentions the deinit-log technique as the cheap first line
  • Ends on prevention, not just detection

Did you know

Xcode's memory graph debugger draws cycles for you.

Pause the app, hit the memory graph button, and filter to your types — a cycle shows as a literal loop in the graph, with the offending references labelled.

Key takeaway

A cycle is a loop of strong references that ARC can't see out of. Decide which object owns which, make ownership point one way, and weaken the reference pointing back.
